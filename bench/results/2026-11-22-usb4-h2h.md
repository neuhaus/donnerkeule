# USB4 host-to-host setting (H2H) on fuzzy and misty, 22 November 2026

Goal: apply AMD's "USB4 H2H Enhancement" ([tools/usb4-h2h](../../tools/usb4-h2h/README.md),
from StrixFold) and rerun the README perftest sweep with it.

Setup: fuzzy (server) and misty (client), Bosgame M5 / Sixunited AXB35-02,
BIOS 1.07, Fedora 43 kernel 7.3.4-100, `amd_iommu=off`, two 0.3 m USB4 cables,
all four links Gen 3 ×2 (`20.0 Gb/s x2`) in every run. Module
`thunderbolt-ibverbs 0.4.0.dk14` with only `roce_netdev=tbv0` (DMA-BUF mode)
or `dmabuf_verbs=0` (native). Stock `thunderbolt.ko` unless noted.
`bench/sweep_perftest.py --seconds 4`, 1 QP, the same commands as the
21 November charts ([scripts/sweep.sh](2026-11-22-usb4-h2h/scripts/sweep.sh)).

## H2H on vs off (stock thunderbolt.ko, same boot)

| Case | H2H off | H2H on | Change |
| --- | ---: | ---: | ---: |
| DMA-BUF WRITE 4 MiB | 38.6 Gb/s | 60.8 | +58% |
| DMA-BUF WRITE 8 MiB | – | 64.5 | |
| DMA-BUF SEND 4 MiB | 43.0 | 60.9 | +42% |
| DMA-BUF bidirectional WRITE 4 MiB | 79.1 | 118.9 | +50% |
| DMA-BUF bidirectional WRITE 8 MiB | – | 130.4 | |
| native WRITE 4 MiB | 44.9 | 54.1 | +21% |
| native READ 1–4 MiB | 9.8 | 25.8 | ×2.6 |
| native bidirectional WRITE 4 MiB | 94.2 | 91.5 | −3% |
| native SEND 256 KiB | 25.2 | 25.9 | +3% |

Busy cores at 4 MiB with H2H: DMA-BUF 1.4 client / 0.5 server (WRITE),
native 4.0 / 3.9 (WRITE), 7.0 / 7.5 (bidirectional).

Reading: without H2H each DMA path stops at about 10–11 Gb/s. A single-path
READ sat at 9.8 Gb/s at every size, and four rails × ~11 Gb/s is where both
modes stopped (~42–45 Gb/s), so the earlier README comparison between the
modes measured that cap. With H2H, DMA-BUF reaches 61–66 Gb/s one way
(about 80% of the 80 Gb/s line rate of two Gen 3 ×2 cables) and 130 Gb/s
both ways on 1.4–1.9 cores. Native mode becomes CPU-bound at about 4 cores
per host (7 bidirectional), and its SEND is limited by the receiver
(5 cores). Small messages (≤ 4 KiB) did not change beyond the noise of
4-second runs.

8 vs 16 MiB with H2H: DMA-BUF −1.5 to −2.4%, native bidirectional −8%,
native WRITE flat. Possibly cache footprint (128 messages in flight), not
tested.

## Which bits matter

H2H sets bits 14 and 15 of register `0xD44EC` in both USB4 routers. With an
experimental build of the module (`xmask`/`xvalue`, not in the repository),
each value written to both routers and the routers reset, on a patched
`thunderbolt.ko` (see below; compare within the table only):

| Bits set | DMA-BUF WRITE 4 MiB | DMA-BUF bidir 4 MiB | native READ 1 MiB |
| --- | ---: | ---: | ---: |
| none | 39.0 | 84.9 | 9.9 |
| 15 | 39.2 | 80.9 | 9.7 |
| 14 | 45.1 | 97.3 | 17.3 |
| 14 + 15 (H2H) | 60.6 | 119.5 | 19.7 |
| 13 + 14 + 15 | 64.4 | 120.0 | 19.8 |
| 14 + 15 + 16 | 60.3 | 119.6 | 19.5 |

Bit 14 lifts the per-path cap; bit 15 only matters on top of it. Bits 13 and
16 showed no clear effect (bit 13's +6% one way was across a reboot, its
other two cases unchanged). The SMU accepted every value; nothing hung.

## Side finding: the ring-interrupt flush fix costs native mode

The NHI lost-interrupt fix (`ioread32` after `REG_RING_INT_CLEAR`,
[tools/thunderbolt-ringfix](../../tools/thunderbolt-ringfix/README.md), patch 0002, installed as DKMS `thunderbolt-ringfix`)
was rebuilt for 7.3.4 and measured against the stock module, swapped twice
on one boot with H2H off:

| native WRITE 4 MiB | stock | ringfix |
| --- | ---: | ---: |
| one way | 44.88 / 44.89 Gb/s, 3.0 client cores | 38.42 / 38.47 Gb/s, 4.85 client cores |
| bidirectional | 86.0 / 93.0 | 60.9 / 61.4 |

It removed the ~70 ms timeout retransmits (`reason=1`) and native small
SENDs gained ~65%, but native bandwidth fell 14% (one way) and ~30%
(bidirectional). DMA-BUF peak bandwidth was unchanged; small DMA-BUF latency
rose about 3 µs (not confirmed on one boot). The ringfix was removed again
from both hosts.

Later the same day a reworked fix (v3: clear the status in `ring_work()`,
hand out the completed frames, then flush and scan again) removed the cost
and still fixed the stalls (0 of 3000 exchanges over 10 ms). With H2H on,
native WRITE 4 MiB went from 54 to 70–73 Gb/s and bidirectional from ~99 to
113–122 Gb/s, with half the interrupts. DMA-BUF and `thunderbolt_net` were
unchanged. It is installed on both hosts as `thunderbolt-ringfix 7.3.4.2`.

## Final sweep: H2H + ringfix (the README charts)

Same sweep with H2H and `thunderbolt-ringfix 7.3.4.2`, 64 B–16 MiB, compared
with the stock-driver H2H sweep:

| Case | stock + H2H | ringfix + H2H |
| --- | ---: | ---: |
| DMA-BUF WRITE 4 / 8 / 16 MiB | 60.8 / 64.5 / 63.0 Gb/s | 61.9 / 65.8 / 65.5 |
| DMA-BUF bidirectional 8 MiB | 130.4 | 129.9 |
| native WRITE 4 / 8 / 16 MiB | 54.1 / 53.3 / 53.0 | 74.5 / 74.6 / 74.8 |
| native bidirectional 8 / 16 MiB | 99.5 / 91.3 | 116.2 / 115.7 |
| native READ 1–8 MiB | 25.8–26.0 | 31.0 |
| native WRITE latency 64 B / 4 KiB | 8.2 / 9.6 µs | 7.1 / 8.8 |
| DMA-BUF WRITE latency 64 B / 4 KiB | 30.0 / 27.2 µs | 27.9 / 23.7 |

Native WRITE uses ~5.7 busy cores on the sender and ~4.2 on the receiver at
these rates; DMA-BUF stays at 1.4 / 0.5. Native `ib_write_bw` at 16 KiB and
`ib_read_bw` at 16 MiB failed again (RNR retransmits, `reason=2`), so they are
not caused by the `thunderbolt` driver.

## Failures

- native `ib_read_bw` 16 MiB with H2H: no result (one run).
- native `ib_write_bw` 16 KiB (one way or bidirectional) fails now and then,
  with RNR retransmits (`reason=2`) on misty; seen with the stock and the
  patched `thunderbolt.ko`.

## Files

- `sweep/base-*.csv`: H2H off, stock, 64 B–4 MiB (this boot's baseline);
  `sweep/2026-11-21-dk14-*.csv`: the 21 November chart sweep it repeats.
- `sweep/h2h-*.csv` + `sweep/h2h-big-*.csv` (8 and 16 MiB): H2H on, stock.
- `sweep/h2h-rep-*.csv`: three repeats of 4 MiB WRITE and 64 B SEND latency
  (DMA-BUF within 0.5%).
- `sweep/rf-h2h-*.csv`: H2H on with the first ringfix (read-back per interrupt).
- `sweep/rf3-h2h-*.csv`: H2H on with `thunderbolt-ringfix 7.3.4.2`; with
  `ib-fdr.csv` these make `sweep/charts.csv`, the source of the README charts.
- `quick/`: the bit tests (`q-off`, `q-ref`, `q-b0x4000`, `q-b0x8000`,
  `q-b13`, `q-b16`) and the stock/ringfix swaps (`q-fix1`, `q-stock`,
  `q-off-abab`).
- `scripts/`: the drivers of these runs (they expect `fuzzy`/`misty` over
  SSH and write to the client's `/tmp`).
