# thunderbolt-ibverbs: critique and improvement plan

13 November 2026

## Summary

The driver works and is fast, but it is expensive to change: one 10,672-line file holds six concerns, the two most delicate code paths are a duplicated send loop and a 276-line state machine, and nothing but manual two-host runs exercises the data path. The recommended order is safety net first, then deletion, then performance.

1. **Build a safety net.** A scripted hardware qualification, a written lock order with lockdep assertions, and a software loopback ring so the native data path runs in a VM under lockdep and KASAN.
2. **Remove the Apple transport.** This fork does not use it. Removal takes out about 16 % of the kernel code, 20 of 60 module parameters, 30 counters and the whole backend abstraction, and makes every later step smaller.
3. **Shrink the option surface.** Make the qualified DMA-BUF options the default, fold five bring-up switches into one, keep one profiling mechanism, and generate counters from one list. Target: a working setup from five options.
4. **Fix the native transmit path.** Today each 4 KiB frame costs three allocations and two copies, about 4 million allocations and 5.5 GB/s of extra copying at 44 Gbit/s. Building straight into the DMA staging frames removes both. This is the largest expected CPU saving and is not yet measured.
5. **Split `ibdev.c` and take the global mutex and shared counters off the per-frame path.**
6. **Turn the DMA-BUF transmit function into an explicit, unit-tested state machine**, then look at small-message latency.

Everything here comes from reading the code at `040214c`. Apart from the RDMA READ test on the lab hosts, nothing was built or measured, so the performance items are hypotheses with a named measurement each, and the line counts for removals are estimates.

## Project as it stands

The driver is 29,300 lines of C in `kernel/` and `proto/`, and one file, `kernel/ibdev.c`, holds 10,672 of them (36 %). Reviewed at commit `d94fa1d` on `main` (code unchanged since `d94fa1d`; `040214c` updates documentation only), by reading the sources only: nothing was built, loaded or measured for this document.

| Area | Size | What it holds |
| --- | --- | --- |
| `kernel/ibdev.c` | 10,672 lines, 326 functions | Verbs device, QP lifecycle, native SEND/WRITE/READ, ACK/RNR/timeouts, reassembly, Apple TX/RX, GSI/MAD, DMA-BUF glue, device registration |
| `kernel/verbs_dmabuf.c` | 3,242 lines | DMA-BUF verbs engine: descriptors posted straight to the NHI rings |
| `kernel/path.c` | 2,687 lines | Ring ownership, TX queues and scheduler, credits, RX dispatch |

The module exposes 60 parameters and keeps 136 global and 21 per-path `atomic64_t` counters. `ibdev.c` and `tbv.h` are the two most-changed files in the history (97 and 91 of 370 commits).

The audit of 7 October (`docs/REFACTOR_AUDIT_2026-10-07.md`) already removed dead code, split out MR and CQ, separated the control ring storage and introduced `tbv_dmabuf_engine`. This document starts from that state and does not repeat those items.

## Pain points

Seven things make the driver hard to change safely. They are ordered by how much they cost per change.

### 1. `ibdev.c` mixes six concerns behind one QP object

`struct tbv_qp` (`ibdev.c:405`) carries native reliability state, Apple FA57 state, DMA-BUF drain state and a 12 KiB ACK history in one struct. It has four locks (`lock`, `rx_lock`, `ack_lock`, `post_lock`) and eleven `bool` flags that together form an unwritten state machine. The file takes a lock 121 times and takes the global `state->lock` in 19 places. No comment or document states the lock order.

A change to native RNR retry has to be read around Apple TX window handling in the same struct and the same file. 54 functions and 389 lines mention Apple, a transport this fork does not use.

### 2. The native send path exists twice

The loop that cuts a message into 4 KiB frames is written once in `tbv_native_send_build_chunk` (`ibdev.c:4645`, asynchronous, per rail) and again in `tbv_native_send_ctx_post_frames` (`ibdev.c:5102`, synchronous). The second function is 337 lines, keeps seven parallel arrays indexed by path, and has its own partial-enqueue unwinding. The two copies differ in reservation and reference handling, so a fix to one does not reach the other. Commit `615c103` (back-pressure) had to touch exactly this split.

### 3. The DMA-BUF transmit state machine is one 276-line function

`tbv_dmabuf_tx` (`verbs_dmabuf.c:2703`) holds PREPARE, credit commit, post, DMA wait, STATUS/DONE and abort in three nested retry loops. Two `goto` labels (`prepared`, `posted`) jump into the loop body so that a direct post from `ibv_post_send` can resume there. Waiting is done by `usleep_range` polling in two places.

The engine is one module-global object with five mutexes and two spinlocks; the only ordering note is a one-line comment. The last two fixes in this area (`5490050`, `d94fa1d`) were both cancel and teardown interleavings in this function family.

### 4. Sixty module parameters, and the working setup needs about twenty of them

The documented Strix Halo configuration sets 17 options on top of defaults. Every DMA-BUF improvement since October is opt-in, so the default build runs the slowest and least-exercised combination. Some options silently depend on others: `tbv_dmabuf_credits_enabled()` returns false without a message unless `dmabuf_push_done=1` and `dmabuf_control_ring=0`.

Five bring-up switches (`bind_services`, `allocate_rings`, `start_rings`, `negotiate_native`, `enable_tunnels`) default to off and only make sense all on. `dmabuf_verbs=1` refuses to load unless every one is set. Open question: the README's short option lines omit them; I did not check on hardware whether those lines work as written.

### 5. The fast path depends on private Thunderbolt internals

`tbv_dmabuf_post_bulk` (`verbs_dmabuf.c:1130`) writes NHI descriptors and the doorbell register itself. It asserts `sizeof(struct tb_ring) == 184` and two field offsets, hard-codes the register layout, and is compiled only for Linux 7.2 and 7.3 on AMD `158d/158e`. `nhi_interrupt_throttle_ns` needs a symbol that only patched kernels export. Eight out-of-tree Thunderbolt patches and the separate `thunderbolt-ringfix` DKMS package sit next to that.

Each kernel minor release therefore needs a manual layout check and a hardware requalification before the measured performance is available again.

### 6. The tests pin the code they should free up

`tools/ci/smoke_support.py` extracts production functions from the C files by regular expression and compiles them against shims. The shims redeclare kernel structs inside Python strings, for example `struct tbv_dmabuf_batch` in `verbs-dmabuf-cancel-smoke.py`. A shim struct can drift from the real one without failing, and moving or renaming a function breaks the test rather than the build. Nothing runs real concurrency: lock order and teardown races are covered only by the two-host hardware runs.

### 7. Observability is hand-wired three times

Each of the 136 global counters is a field in `tbv.h`, an increment somewhere, and one of 204 `seq_printf` lines in `debugfs.c`. Two profiling mechanisms bracket the same DMA-BUF phases: `dmabuf_profile` (`tbv_dmabuf_clock`/`tbv_dmabuf_record`) and the `tbv_perf` tracepoints, so most phases in `tbv_dmabuf_tx` take two timestamps and two record calls.

### Smaller friction

- `bench/results/` is 5,281 tracked files and 84 MB in the working tree, including four full copies of an old `verbs_dmabuf.c`. Packaging and Nix filters have to step around it.
- The version is stated in `dkms.conf`, four times in `flake.nix` and in two spec files. Lab installs use hand-made `0.4.0.dkN` versions. The README still points at upstream's `0.3.0` provider package.
- `make -C kernel help` lists parameters by hand and names none of the 18 `dmabuf_*` options.
- `module.nix` (NixOS module, 593 lines) and `nix/module.nix` (package, 56 lines) share a name and nothing else.

## Refactoring

Five restructurings, each of which removes one of the pain points above without changing wire behavior.

### R1. One frame builder for native sends

Keep `tbv_native_send_build_chunk` as the only code that turns a byte range of a send into queued frames. The synchronous path becomes a call to it per path with the same reservation contract, and `tbv_native_send_ctx_post_frames` shrinks to path selection plus the zero-copy special case. The seven parallel arrays and the partial-enqueue unwinding disappear, because a chunk either queues completely or returns `-EAGAIN`.

### R2. Split `ibdev.c` along its transports

The 7 October audit moved MR and CQ out and named Apple and reassembly as the next step. The cut lines are already visible in the function list:

| New file | Moves out of `ibdev.c` | About |
| --- | --- | --- |
| `verbs_apple.c` | Apple send queue, TX window, pending RX, raw CRC, `tbv_ibdev_rx_apple_frame` | 1,900 lines |
| `verbs_native_tx.c` | Send context, segments, frame building, zero-copy stream, post_send | 2,300 lines |
| `verbs_native_rx.c` | Reorder table, SEND/WRITE/block-write fragments, ACK and credit frames, RX dispatch | 2,600 lines |
| `verbs_read.c` | RDMA READ request, response, retry | 900 lines |
| `verbs_qp_timer.c` | Timeout work and the three reap functions | 700 lines |
| `verbs_gsi.c` | GSI/MAD send and receive | 350 lines |
| `ibdev.c` (rest) | Device ops, QP create/modify/destroy, rail registration, netdev notifier | 2,000 lines |

With the Apple transport removed first (S4), the `verbs_apple.c` row disappears: that code is deleted, not moved, and `struct tbv_qp` needs no per-backend split. The remaining struct should still group its fields by owner (`tx`, `rx`, `timer`) so each new file touches one group.

### R3. Make the DMA-BUF transmit an explicit state machine

Replace the loop-with-gotos in `tbv_dmabuf_tx` by one function per phase (`build`, `arm`, `post`, `wait_dma`, `wait_done`, `finish`) and a small driver that switches on an enum, mirroring what `tbv_dmabuf_rx_state` already does for receive. A direct post then enters at `wait_dma` by setting the state, not by jumping into a loop. The cancel rules that `5490050` and `d94fa1d` introduced become transitions that can be read and tested in one place.

Put the transition function (state, event) to (state, action) into `proto/` as pure C, the way `proto/reliability.c` already holds the native reliability rules. It then compiles into both the module and a real unit test.

### R4. Write down and enforce the lock order

Add a `Locking` comment block at the top of `verbs_internal.h` and `verbs_dmabuf.c` with the order as the code uses it today, and add `lockdep_assert_held()` to every `*_locked` function (there are 54 in `ibdev.c`). The whole module has one such assertion today, and the VM smoke kernels enable neither lockdep nor KASAN. A lockdep-enabled VM run then checks the order on every change. This is cheap and should come before R2 moves code around.

### R5. Give tests a seam instead of a regular expression

Move decision logic that the Python smoke tests extract today (cancel decision, RX state transitions, control transaction lifetime, configfs activation) into `proto/`-style files with no kernel types in their interface. Tests include the real header and link the real object. The remaining extraction tests can then be deleted one at a time; `smoke_support.functions()` should end with no callers.

## Simplification

Six things can be removed or merged outright.

### S1. Turn qualified options into defaults and group the rest

The options below have passed the 16 and 25 October qualifications and are part of the documented setup. Make them the default when `dmabuf_verbs=1`, keep each as an off switch for one release, then delete the switch.

| Today | Proposal |
| --- | --- |
| `bind_services`, `allocate_rings`, `start_rings`, `negotiate_native`, `enable_tunnels` | One `bringup=full` parameter that sets all five |
| `dmabuf_push_done`, `dmabuf_credits`, `dmabuf_coalesce_copy`, `dmabuf_reuse_buffers`, `dmabuf_host_direct`, `dmabuf_host_credits` | On by default in DMA-BUF mode. A dependency that is not met fails the load with a message. |
| `dmabuf_batch_doorbell`, `dmabuf_post_burst` | `auto`: on, with burst 128, where the NHI and kernel are supported; otherwise off with one log line. |
| `dmabuf_rx_eager`, `dmabuf_parallel_post`, `dmabuf_index`, `dmabuf_direct_post` | Already default on. Remove the switch and the slow branch. |
| `dmabuf_control_ring` | Measured slower on the tested NHIs and default off. Remove it with `tbv_control_ring` (the ring half of `verbs_control.c`), or move it to a branch. |
| `apple_tx_max_inflight_wr` | Described as deprecated in `make help`. Remove. |

The target is a working two-cable setup from `profile=linux_perf lanes=2 register_verbs=1 dmabuf_verbs=1 roce_netdev=...`, with the parameter count near 30.

### S2. One profiling mechanism

Keep the `tbv_perf` tracepoints, which carry per-WR identity, and delete `dmabuf_profile` with its 17 phase accumulators. `tools/tbv-profile-report.py` already aggregates trace output; the debugfs phase totals can be produced from it. Every phase in the transmit path then takes one timestamp, not two.

### S3. Generate the counters

Declare the counters once in an X-macro list (`TBV_COUNTER(data_rx_lost)`), and expand it into the struct, the debugfs printer and the `make help`-style documentation. This removes about 200 hand-written `seq_printf` lines and makes a forgotten debugfs line impossible. It is also the precondition for the per-CPU change in the optimization section.

### S4. Remove the Apple transport

This fork does not target Apple peers, so the Apple FA57 transport and the ThunderboltIP identity code that exists only for it should be deleted, not isolated. It is the largest single simplification available: about 4,500 to 5,000 of 29,300 kernel lines (16 %), 20 of 60 module parameters and 30 counters.

| What goes | Size |
| --- | --- |
| `tbnet_identity.c`, `tbnet_minimal.c`, `apple.c`, `proto/apple_tx.h`, `proto/tbnet.h` | 2,720 lines, whole files |
| Apple functions in `ibdev.c` (send queue, TX window, pending RX, raw CRC, tunnel refcount, RX frame handler) | 1,250 lines of function bodies, plus fields and branches |
| Apple property directory and service handling in `service.c`, Apple lines in `debugfs.c`, `profile.c`, `main.c` | about 500 lines |
| Parameters: 12 `apple_*`, 5 `tbnet_identity*`; `compat`, `profile` and `tbnet` lose their purpose | up to 20 of 60 |
| Counters: 15 `apple_*` in `tbv_state`, 15 in `tbv_tbnet_identity` | 30 |
| Backend abstraction: `backend.c`, `transport.h`, `tbv_backend_ops`, the `backend` field on peer, QP, device and configured link | 44 backend checks in 9 files |
| Userspace and Nix: `mac_tb_rdma_probe.c`, `nix/apple-compat/`, the Apple perftest patch, Darwin outputs in `flake.nix` | about 1,400 lines |

What this buys beyond the line count:

- **A smaller QP.** `struct tbv_qp` loses the Apple send queue, TX window counters, pending-RX ring, tunnel flag and discard flag. `struct tbv_send_ctx` loses six fields and a `delayed_work`. The eleven-flag state machine from pain point 1 gets shorter.
- **Fewer teardown orders to get right.** The Apple tunnel reference, `apple_rail_work`, the wait-for-tbnet deferral, two netdev notifiers and an RX handler all have their own start and stop ordering today. They disappear, and with them a class of bugs like the ones fixed in the DMA-BUF teardown.
- **No per-frame backend dispatch.** `tbv_path_rx_complete`, the TX in-flight limit, the poll decision and `post_send` each test the backend per frame or per WR. The CPU gain is small; the gain is that the native path reads straight through.
- **A cheaper R2.** The file split has 1,900 fewer lines to move, and `struct tbv_qp` needs no per-backend split.
- **A smaller test surface.** VM smoke, `config-smoke`, `verbs-smoke` and the perftest runner drop their Apple and Darwin cases, and the `mac_compat`/`mixed` profile combinations stop existing.

What stays: UC queue pairs (the native backend supports them), `proto/identity.c` (configfs uses it for GIDs), and the native raw-stream zero-copy path, which is not Apple code despite sitting next to `apple_tx_raw_mode`.

Two costs. Merges from upstream `hellas-ai/thunderbolt-ibverbs`, which wrote 277 of the 371 commits, will conflict wherever upstream touches Apple code; after this step the fork takes upstream changes by cherry-pick only. And one thing to verify before deleting: `native.c` declares `needs_tbnet_identity = false`, but I did not trace whether the `tbnet=` policy still affects native ring allocation. Keep that parameter until a load with `tbnet_identity=off` is confirmed to behave the same on fuzzy and misty.

### S5. Move measurement archives out of the source tree

Keep the 13 Markdown reports under `bench/results/` and move the raw logs (5,200 files) to a separate `donnerkeule-results` repository or release assets, linked from each report. The reports stay reviewable; clones, DKMS source copies and Nix source filters stop carrying 84 MB of logs and four stale copies of driver source.

### S6. One version, one parameter list

Read the version from a single `VERSION` file in `dkms.conf` generation, `flake.nix`, the spec files and `MODULE_VERSION`. Generate the `make help` parameter list from `modinfo` output of the built module so it cannot go stale. Rename `module.nix` to `nixos-module.nix`.

### S7. Require the same build on both hosts

The module has no notion of the lab versions dk1 to dk6. None of the four wire version numbers changed across them, so they interoperate by accident, not by design. The one wire-relevant change in that range was the message size limit (192 MiB in `e03d836`, 248 MiB in `f945ede`): an older peer rejects the larger messages with a bad-header error and no hint that the builds differ.

What the code does carry is compatibility with older and differently configured peers. Since this fork needs none of it, it can go:

| Compatibility code | Where | After removal |
| --- | --- | --- |
| HELLO version 1 parsing, for peers without host and domain ids | `proto/native_wire.h`, `has_ids` branches in `native_control.c`, the ambiguity limits in `peer.c` (`tbv_native_legacy_*_allowed_locked`), one counter, one warn-once flag | Ids are always present; `remote_host_known` is set once at HELLO |
| Optional per-path sequence number (`TBV_NATIVE_DATA_PATH_SEQ_PRESENT`, "ignored by older peers") | `path.c:843`, `path.c:1974` | Sequence is always present and always checked |
| Per-feature capability bits for control ring, pushed DONE and credits, with a mixed-mode branch at each use | `native_control.c`, `verbs_control.c`, `verbs_dmabuf.c` (`remote_control_ring`, `remote_push_done`, `remote_dmabuf_credit`) | With the S1 defaults both ends always agree; the three flags and their fallback paths are deleted |
| Rejection of the removed `GPU_DIRECT` capability | `native_control.c`, three places | Covered by the revision check below |

Replace all of it with one protocol revision number in HELLO that must match exactly, bumped on every wire or semantic change, with a clear log line on mismatch (`peer speaks revision N, this build M: install the same build on both hosts`). That turns the silent 192/248 MiB kind of mismatch into an immediate, readable failure.

Keep the source-blind XDomain handler in `native_control_legacy.c`. Despite the name it is not peer compatibility: it is what the module uses on stock kernels that lack the source-aware handler patch. Also keep the build-time kernel probes.

Do this in Phase 2 after the defaults change (step 3), since the capability bits only become constant then. Gate: `proto-smoke` updated, loopback tests, a deliberate mismatch test that shows the log line, then qualify.

## Optimization

Native mode spends its CPU on per-frame bookkeeping, not on the wire: the README reports 3 to 8 busy cores for native against 1.3 to 1.9 for DMA-BUF mode at similar bandwidth. The items below come from reading the code. None is measured; each names the measurement that would confirm it.

### O1. Native TX copies every payload twice and allocates three times per frame

For each 4 KiB frame of a WRITE or SEND the driver today does this:

1. `kmalloc` a 4 KiB frame buffer and copy the payload from the MR into it (`ibdev.c:4675`).
2. `kzalloc` a `tbv_path_owned_frame` list node (`ibdev.c:4695`).
3. `kzalloc` a `tbv_tx_packet`, which embeds a 256-byte control buffer it does not use (`path.c:1443`).
4. In the scheduler, `memcpy` the frame into a pre-mapped DMA staging frame (`path.c:1966`).
5. Free all three after completion.

At 44 Gbit/s that is about 1.3 million frames per second: 4 million allocations and 5.5 GB/s of avoidable copying. The staging frames are already allocated and DMA-mapped per ring. Let the build worker take a free staging frame and copy from the MR straight into it; the packet metadata can live in `tbv_data_frame`. Result: one copy, no allocation. Confirm with `perf top` on the sender during a 4 MiB `ib_write_bw` run: `memcpy`, `kmalloc` and `kfree` shares before and after.

### O2. The TX scheduler and completion work one frame at a time

`tbv_path_schedule_tx` takes `tx_lock` twice per frame, calls `tb_ring_tx` per frame, and calls `queue_delayed_work` twice per posted frame for the two poll workers. Each completion takes `tx_lock` again, then `tqp->lock` in `tbv_send_retire_frames`, then drops one send reference. Dequeue up to 64 packets per lock hold, arm the poll workers once per batch, and retire a send's frames once per ring-work run with a count. Confirm with lock statistics (`lock_stat`) on `tx_lock` and `tqp->lock`.

### O3. A global mutex sits on the send and ACK paths

`state->lock`, the mutex that guards peer and rail lifetime, is taken for path selection on every `post_send` (`ibdev.c:4992`, `5041`) and for every ACK or credit frame sent (`ibdev.c:6377`). All QPs and all four rail workers serialize on it. Publish each peer's ready paths as an RCU-protected array that rail up/down events replace; the hot paths then read it under `rcu_read_lock` and take a rail reference. Confirm with `lock_stat` contention counts on `state->lock` under bidirectional 64 KiB traffic.

### O4. Shared counters bounce between the rail workers

A data frame increments roughly ten global `atomic64_t` counters on its way out and in (`data_tx_posted`, `data_tx_completed`, `data_rx_completed`, `data_wr_path_send`, `data_rx_send`, the per-opcode counters) plus their per-path twins. Four RX workers and the build workers write the same cache lines. Make the hot counters per-CPU and sum them when debugfs is read. Confirm with `perf c2c` on the receiver.

### O5. The receiver repeats lookups for every fragment

Each 4 KiB block-write fragment does a QP lookup under the xarray spinlock with interrupts off, two `rx_lock` acquisitions, two hash lookups, and an MR lookup by rkey with a reference get and put (`ibdev.c:8668`). The header is parsed in `path.c:937` and again in `ibdev.c:9642`. Store the MR pointer in the reorder entry when the message's first fragment arrives, pass the parsed header through, and look the QP up under RCU. A 4 MiB WRITE then does one MR lookup, not 1,024.

### O6. DMA-BUF small-message latency comes from sleeping polls

Small WRITEs and SENDs take about 30 µs in DMA-BUF mode. The transmit path hops to a worker, exchanges PREPARE over XDomain, and on a busy or RNR answer sleeps 1 to 2 ms (`usleep_range(1000, 2000)`, `verbs_dmabuf.c:2851`); without pushed DONE it polls STATUS every 100 to 200 µs. Credits and direct post already remove the worker hop and PREPARE for credited SENDs. Two candidates to measure after R3: wake the sender from a BUSY-cleared notification, as `credit_wait` already does for RNR, and let small WRITEs use the same credit path. The single RX transaction per host is a protocol limit and is not addressed here.

### O7. Smaller items

- A build job that finds the path queue full retries after one jiffy (`TBV_SEND_BUILD_RETRY_JIFFIES`). Waking it from TX completion when the queue falls below half removes the dependence on `HZ`.
- `struct tbv_qp` embeds a 1,024-entry ACK history (12 KiB) and each reorder entry is up to 8 KiB, zeroed per message. Size the history by the negotiated queue depth and use a `kmem_cache` for reorder entries and send contexts.

## Build, test and tooling

The data path is only ever exercised on the two lab hosts, by hand. That is the gap that makes every refactoring above risky, so it is addressed first in the plan.

### T1. A software ring so the data path runs in a VM

`path.c` calls `tb_ring_alloc_*`, `tb_ring_tx`, `tb_ring_rx` and `tb_ring_poll` directly. Put those calls behind a small `struct tbv_ring_ops` and add a loopback implementation, built only with `TBV_LOOPBACK=1`, that connects two rails inside one kernel and delivers frames from a work item. With it, `rc_write_imm_verify`, `rc_qpn_churn` and QP-destroy-under-load run in the existing QEMU smoke VM. Options for dropping, reordering and delaying frames turn the loss cases of 18 October into repeatable tests. DMA-BUF mode writes NHI descriptors itself and stays hardware-only at first.

### T2. Debug kernels in the VM job

Build the VM smoke kernel a second time with `PROVE_LOCKING`, `KASAN` and `DEBUG_ATOMIC_SLEEP`. Together with T1 and the `lockdep_assert_held` calls from R4, lock-order and use-after-free bugs fail in CI and not on fuzzy.

### T3. One scripted hardware qualification

Each result directory carries its own copy of install and run scripts. Promote them to one `tools/lab/qualify.sh` with a fixed matrix: link speed check on both hosts first, native sweep, DMA-BUF host and GPU matrix, cancel and teardown cases, counters before and after, then a pass/fail summary. Every later step in the plan names this script as its gate, and a run becomes comparable to the previous one.

### T4. Probe the `tb_ring` layout, do not gate on a version

`256dfe7` widened the version gate for the bulk doorbell from 7.2 to 7.3 by hand. The layout assertions already exist as `BUILD_BUG_ON`. Move them into a `compat/tb_ring_layout.c` try-compile probe, the way `compat/tb_service_probe.c` already probes the probe signature. A kernel with the known layout enables the path, any other compiles it out, and no source edit is needed per kernel release. Log one warning when the running kernel is not on the qualified list.

The lasting fix is upstream: the two Thunderbolt fixes carried as `thunderbolt-ringfix`, and a `tb_ring` bulk-enqueue API that would make the private descriptor access unnecessary.

### T5. Smaller tooling items

- Derive the DKMS version from `git describe` in a `make dkms-version` target; stop hand-numbering `0.4.0.dkN`.
- Run `tools/ci/run-smoke.py` in the GitHub workflow as its own job, so a pull request shows a smoke failure separately from a packaging failure.
- Replace the dated status documents with one `docs/ARCHITECTURE.md` (components, lock order, the two state machines, wire formats) and move the dated ones, including the two German audit files, to `docs/history/`.

## RDMA READ above 512 KiB

**Finding.** There is no size limit. The code accepts a READ up to 248 MiB (`ibdev.c:9112`). A READ fails when the total of outstanding READ bytes on the QP cannot be delivered within the requester's ack timeout. `ib_read_bw` keeps 128 READs outstanding and sets a timeout of about 67 ms, so 512 KiB (64 MiB in total) is the largest size that still drains in time on one rail.

Measured on 13 November 2026 on fuzzy and misty: native mode (`dmabuf_verbs=0`), kernel 7.3.3, both cables at 2 x 20 Gb/s, one QP, 10 s per run, `ib_read_bw` on `usb4_rdma0`.

| 18, about 1.07 s | 1 MiB x 128 | Passes at 625 MiB/s, with 4,900 response retransmits and 1.26 million duplicate frames |

### Mechanism

- **Requester timer.** Each READ gets one timer, started when its request frame has been sent (`ibdev.c:1353`) and checked in `tbv_qp_timeout_reap_tx` (`ibdev.c:3698`). It uses the QP's ack timeout, is not restarted when response frames arrive, and has no retry. When it expires the READ completes with a timeout and the QP goes to error. In every failure at default settings, `data_wr_timeout` and `data_rx_qp_error` on the requester are the only counters that move.
- **One rail.** All responses of a QP leave on the rail the request arrived on, at about 1.15 GB/s. 64 MiB drains in about 58 ms and 96 MiB in about 87 ms, on either side of the 67 ms timeout. Disabling write striping changes nothing.
- **No loss.** Read-response gaps, lost frames, bad frames and CRC errors stay at zero in every run. The per-frame RETRY acknowledgements after a gap (`ibdev.c:9304`) are still a design weakness but play no part here.
- **Responder resend.** The responder starts its own timer when a response is queued, not when it reaches the wire, and resends the whole response after min(100 ms, QP timeout), up to 3 times. At default settings the requester fails first, so this never fires. With a longer requester timeout it does fire, and the resends enter the same queue: the run passes but at about half the throughput.
- **`max_rd_atomic` is not enforced.** The module stores the value in `modify_qp` and never uses it. The requester sends as many READs as the send queue holds, so perftest's `-o` is ignored and 128 are always in flight.

### Fix

1. Enforce `max_rd_atomic` on the requester: hold further READs in the send queue until earlier ones complete. This bounds the outstanding bytes and is what the verbs contract promises.
2. Restart the requester's READ timer whenever a response frame for that READ arrives. A READ that is making progress must not time out.
3. Start the responder's resend timer when the last response frame has left the ring, not when the response is queued.
4. Send one RETRY per gap, not one per out-of-order frame, and resend from the missing offset.
5. Raise the sweep cap for `ib_read_bw` in `bench/README.md` above 524288.

This work only pays off if native mode stays (see the open decision below). DMA-BUF mode has no RDMA READ at all.

Before the test the analysis blamed the responder's resend timer, or a RETRY storm after a lost frame. The measurements ruled out both as the cause of the failure at default settings.

## rdma_cm: what it needs and what it gains

**Verdict.** rdma_cm is a connection-setup convenience. It changes nothing on the data path, so it gains no throughput for Gufo, StrixFold or hipfire. In native mode most of the driver side already exists and may work after a short test. In DMA-BUF mode, which is the mode that matters, three concrete gaps block it. It should rank below DMA-BUF error recovery and concurrency. For the projects that still need USB4 TP=2 support, a small shared link library is worth more than rdma_cm.

Nothing in this section was run on the lab hosts. Statements about the RDMA core's behaviour are from knowledge of the kernel and need the test in step 1 to confirm them.

### What the driver has today

| Piece rdma_cm needs | Native mode | DMA-BUF mode |
| --- | --- | --- |
| RoCE v2 port with a netdev (`roce_netdev`) | Present | Present |
| GID table filled from the netdev's IP addresses | Done by the RDMA core; the no-op `add_gid`/`del_gid` are enough | Same |
| MAD and CM port capabilities | Advertised | Cleared in `tbv_get_port_immutable` (commit `94f68a9`) |
| Kernel GSI QP (QP1) | Present: `tbv_post_gsi_send`, `tbv_rx_handle_mad`, AH create/destroy | `tbv_create_qp` rejects every type except RC |
| MAD carrier | One native frame (`TBV_NATIVE_DATA_OP_MAD`) on the QP's rail | None: the rings carry raw descriptors |
| Kernel buffers by virtual address | Yes: registered without a DMA device | No: registered with the NHI as DMA device, and the GSI path requires `ib_uses_virt_dma()` |
| `modify_qp` with the masks CM uses | Present | Present |
| Async events (`ib_dispatch_event`) | None anywhere in the module | None |

No test, benchmark or document in the repository exercises rdma_cm (`rping`, `ucmatose`, `ib_send_bw -R`). The native GSI code was written for it but its status is unknown.

### What is needed

1. **Test native mode as it is.** Load `rdma_cm` and `rdma_ucm`, give the `roce_netdev` interface an address on each host, then run `rping` and `ib_send_bw -R`. Three places are likely to fail:
   - Address resolution. `roce_netdev` is usually a dummy interface that carries no packets. Route lookup works locally, and the core skips neighbour resolution for NOARP interfaces, so this should pass, but it is the first thing to check.
   - Device choice. There is one `ib_device` per rail and they all attach to the same netdev, so every device holds the same GIDs. rdma_cm picks a device by source address and cannot tell them apart. Either give each rail device its own netdev and address, or accept that rdma_cm always lands on the first device and let the driver stripe across rails as it does now.
   - Incoming MADs. `tbv_rx_handle_mad` always reports `RDMA_NETWORK_IPV6`. The core then looks up the destination GID in the local table. IPv4 addresses are stored as mapped GIDs, so this may work, but it is untested.
2. **Give DMA-BUF mode a MAD carrier.** CM needs about five 256-byte MADs per connection, plus the 40 bytes of GID and P_Key metadata the native frame already carries. The XDomain control channel that carries PREPARE and READY is the natural place. One MAD does not fit one XDomain packet, so it needs two fragments.
3. **Allow a kernel GSI QP in DMA-BUF mode.** Lift the RC-only check for kernel GSI QPs and restore the MAD and CM capabilities.
4. **Solve the DMA address problem.** In DMA-BUF mode the device is registered with the NHI as its DMA device, because user DMA-BUF MRs go through the core's `ib_umem_dmabuf` attachment. Kernel users such as `ib_mad` then pass DMA addresses, which the GSI path cannot turn back into pointers. The clean fix is to register the device as a virtual-DMA device in both modes and attach user DMA-BUFs to the NHI explicitly (the module already calls `dma_buf_attach` itself for the per-rail maps in `verbs_dmabuf.c:586`). This also removes one difference between the two modes.
5. **Dispatch async events.** Raise `IB_EVENT_PORT_ERR` and `IB_EVENT_PORT_ACTIVE` when a rail is quarantined or returns, and a QP fatal event when a QP is moved to error. rdma_cm and plain verbs applications both use these to learn about a failure without waiting for a timeout.
6. **Add it to the tests.** `rping` as a load-time check and `-R` variants in the bench sweep.

Steps 2 to 4 are the real work. They touch the control channel, QP creation and device registration, so they belong after the DMA-BUF state-machine refactor, not before it. If native mode is frozen as proposed under the open decision below, the GSI code in `ibdev.c` stays but moves to the new carrier.

### What each project would gain

| Project | USB4 RDMA today | Connection setup today | Gain from rdma_cm |
| --- | --- | --- | --- |
| Gufo | Yes. RC QP, DMA-BUF windows exported with `hipMemGetHandleForAddressRange` (`verbs.cpp`, 1,845 lines) | TCP bootstrap socket exchanges QPN, GID, MTU and the receive window's address and rkey. The socket stays open with keepalive as the liveness signal | Removes about 200 lines of socket code and the `--tp-rdma-device`, `--tp-rdma-port` and `--tp-gid-index` flags. No speed change |
| StrixFold | Opt-in on a local branch (`COLL_KIND=verbs`): three RC QPs on one rail, host buffers, TCP remains the default | Ethernet TCP exchanges startup data and stays open to detect a peer exit | Removes the device and GID-index settings. No speed change. The Mac side of the shared code has no librdmacm, so it would be a Linux-only path |
| hipfire | None. TP, EP and PP run inside one process across local cards, using peer memcpy and RCCL all-reduce | Not applicable | Only the bootstrap of a transport that does not exist yet |

What rdma_cm does give all three: the peer is named by IP address, so the device name and GID index disappear from configuration (both Gufo and StrixFold carry GID scanning code for this); a killed peer produces a DISCONNECTED event because the kernel sends a DREQ when the process's CM file closes; and the startup exchange can ride in CM private data (56 bytes on the request), so the USB4 link needs no Ethernet for bring-up.

What it does not give: detection of a host that vanishes without closing anything. That still needs the transport's retry timeout or a keepalive, which is why both projects would keep some form of their TCP liveness channel.

### What the projects without USB4 TP=2 actually need

StrixFold's own measurements show where its gap is. Verbs reaches first output sooner than two-cable TCP, but decodes slower (55.6 against 63.4 tokens/s with drafting) because each payload is copied into a host window, waits for a per-write credit, and is copied out again. The fix is DMA-BUF windows and one QP per cable-side worker, not connection management.

hipfire needs the whole cross-host layer: a rank-per-host launcher, a fabric interface behind `all_reduce_sum_f32_peer_add_routed` and the EP row and tile exchanges, a remote implementation of those collectives, DMA-BUF export of the exchange buffers, and failure handling. Its dense TP2 protocol relies on each rank reading the peer's buffer directly and on peer producer and consumer events. Across hosts that becomes write-with-immediate into a registered window plus a completion, which is the pattern Gufo already uses. Connection setup is the smallest part of that work.

Gufo and StrixFold each wrote the same thing independently: open device, pick GID, bootstrap, connect, register windows, credit, exchange, detect peer death (about 1,800 and 1,400 lines). hipfire would write it a third time, in Rust. A small C library in this repository with a stable C ABI, grown from the existing `tbv_gpu_verbs` harness, would serve all three (C++, Zig and Rust all call C). It would also be the one place that encodes the DMA-BUF mode's contract: RC only, no READ, 256 MiB per exported object, LOCAL_WRITE and REMOTE_WRITE only, one transfer in flight per direction. If that library uses rdma_cm internally later, no application changes.

### Inference engines in general

- **Engines that speak raw verbs with their own bootstrap** gain nothing. RCCL's InfiniBand transport works this way, and the driver's per-rail node GUID comment shows RCCL was already a target. RCCL over this device would be the shortest route to PyTorch-based engines and deserves its own investigation.
- **Engines that speak only TCP** (llama.cpp's RPC server, most Python serving stacks) could use rsocket through its preload library, which requires rdma_cm. This matters because Donnerkeule owns the DMA rings, so stock `thunderbolt_net` cannot run beside it and these engines fall back to Ethernet. rsocket copies through host buffers, so expect TCP-over-Thunderbolt speeds at best, not DMA-BUF speeds.
- **libfabric** needs rdma_cm for its verbs provider, so rdma_cm is a precondition for anything built on it.
- **UCX and MPI** would still not work: UCX's RC transports also need SRQ, and usually UD for wire-up, and the driver supports neither.
- **Kernel storage protocols** (NVMe over Fabrics, NFS over RDMA) need rdma_cm and fast-registration MRs. They would let one host load weights from the other over USB4, but that is a separate project.
- **Standard tools** (`rping`, `qperf`, perftest `-R`) start working, which helps anyone evaluating the driver.

The statements about third-party software are from general knowledge and were not tested against this driver.

### Recommendation

1. Run the native-mode rdma_cm test once. It is cheap and tells whether the existing GSI code works.
2. Add async events (step 5) regardless of rdma_cm. Every verbs application benefits.
3. Build the shared link library and use it to bring USB4 TP=2 to hipfire and to move StrixFold's verbs path to DMA-BUF windows.
4. Do rdma_cm in DMA-BUF mode only when a concrete consumer needs it (rsocket for a TCP-only engine, or libfabric), and after the state-machine refactor.

## DMA-BUF windows: design for applications

A DMA-BUF window is a piece of GPU memory registered directly with the RDMA device, so the NHI reads and writes it and the payload never passes through host RAM. Gufo already does this in `verbs.cpp`, and the driver's contract is in `docs/GPU_VERBS.md`. This section generalises that pattern for StrixFold, hipfire and the shared link library proposed above. StrixFold's GPU staging code was not read in detail, so the parts specific to it are a proposal.

### The window

- **One allocation per window.** Allocate uncached device memory (`hipExtMallocWithFlags` with `hipDeviceMallocUncached`), so nothing sits in a cache between the GPU kernel and the NHI.
- **One DMA-BUF and one MR per window.** Export with `hipMemGetHandleForAddressRange` (`hipMemRangeHandleTypeDmaBufFd`) and register with `ibv_reg_dmabuf_mr`, using the device pointer as the IOVA. Separate windows let the set exceed the driver's limit of 256 MiB per exported object.
- **Access rights.** `LOCAL_WRITE` on the send and the receive set is enough for the SEND-based design. The driver allows nothing beyond `LOCAL_WRITE` and `REMOTE_WRITE`.
- **Two sets per rank.** A send set and a receive set, each a small rotation of K windows. Gufo uses three windows of 48 MiB, because a consumer may still be reading window n when exchange n+2 lands. K is the number of exchanges that can overlap in the engine.

### The transfer

Use `SEND_WITH_IMM` from a send window into a receive WQE that covers a whole receive window, not `RDMA_WRITE_WITH_IMM`.

- **No application credit message.** A SEND consumes a receive WQE, so the driver knows the destination before data moves. With the driver's prepared SEND credits it pre-arms the receive side, which removes the PREPARE round trip. StrixFold's zero-byte credit SEND before every WRITE disappears.
- **No header in the payload.** The payload must start on a 4 KiB boundary. The immediate carries the operation identity and the completion carries the length.
- **Flow control is the receive WQE.** The receiver re-posts a window's receive only after its GPU consumer has finished reading it. That re-post is the credit.
- **Length rules.** One contiguous SGE, offset a multiple of 4096, length padded to 32 bytes, at most 248 MiB per work request. The receive WQE must reserve the span rounded up to a full page.

### GPU ordering

MR registration and the completion queue do not make GPU data visible on their own. The application must order it.

- **Before posting.** The producing kernel must have finished and released to the system. Gufo records a readiness event per exchange and waits for it.
- **After the receive completion.** The consuming kernel may read the window, and nothing may re-arm that window until it has.

### Where the copies go

| Path | Copies of the payload |
| --- | --- |
| Host windows (StrixFold verbs today) | GPU to host, driver staging, host to GPU |
| GPU windows with staging (Gufo today) | One device-to-device copy into the send window |
| GPU windows as kernel output | None: the kernel writes its partial into the send window and the consumer reads the receive window in place |

The last row is the target. The collective's output buffer is then the window itself, so the engine's buffer lifetimes have to follow the window rotation.

### Around the windows

- **Small messages.** Send commands and token IDs through an ordinary host MR on the same QP. The driver stages them, and ordering with the tensor traffic is preserved.
- **One QP for now.** The DMA-BUF engine runs one transfer per direction at a time, and parallel QPs are listed as unqualified. StrixFold's three QPs would only queue behind each other.
- **Negotiation.** At startup both ranks state whether GPU windows work, and fall back to host windows unless both do. Gufo exchanges a small placement record for this.
- **Failure.** A data error stops the affected rails until the modules are reloaded. Treat it as fatal for the pair and report it. Do not retry on the same link.

### Sizing

- **StrixFold.** Its prefill gathers reach 200 MiB, which fits one window and one work request, so the 4 MiB chunking can go. Decode gathers are small; there the gain is the removed credit round trip and the removed copies.
- **hipfire.** Dense TP2 decode exchanges one partial per layer for attention and one for the FFN, in different buffers. Two rotations of small windows map onto that directly. The peer's producer and consumer events become the readiness event and the receive re-post.

## Open decision: DMA-BUF as the only data path

DMA-BUF-only is the right end state for this fork's workload, but the path is not ready to stand alone yet. Decide before Phase 3, because the answer determines whether the native optimizations are worth doing.

What it would remove: the native framed data path, meaning send building, reassembly and reorder, ACK/RNR/retransmit, credits, RDMA READ, the QP timer, most of the TX queueing in `path.c` and `proto/reliability.c`. That is roughly 8,000 further lines, and it makes R1, O1 to O5 and most of Phase 4 unnecessary. DMA-BUF mode already bypasses all of it and keeps only ring setup, the HELLO handshake and the QP, MR and CQ objects.

What native still does that DMA-BUF does not, from the README, `GPU_VERBS.md` and the code:

| Gap | Native | DMA-BUF today |
| --- | --- | --- |
| Error recovery | A lost or corrupt frame is retransmitted | A data error or abort stops the rails until both modules are reloaded |
| Concurrency | Many QPs, per-rail workers | One TX stream and one RX transaction per host; parallel QPs are not qualified |
| Small messages | Lower latency up to 32 KiB, higher bandwidth below 4 MiB | About 30 µs per small WRITE or SEND |
| Verbs coverage | RDMA READ, MAD/CM | No READ, no MAD/CM |
| Portability | Public `tb_ring` API | Full speed needs the private ring layout on AMD `158d/158e`, Linux 7.2 and 7.3 |

The first two are the blockers. A transport whose only response to one bad frame is a module reload on both hosts cannot be the sole path, and the applications the README advertises (NCCL, UCX, vLLM with several QPs) need concurrent QPs. The latency and READ gaps matter only if a workload other than Gufo is in scope.

Recommended course:

1. Freeze native now: bug fixes only. Skip Phase 3 and the native parts of Phase 4. Keep native as the fallback and as the A/B reference while DMA-BUF matures.
2. Do Phase 5 (the explicit transmit state machine) earlier, since it is the base for the next two items.
3. Make a failed batch recoverable without stopping the rails: re-arm and resend the batch after a data error, and quarantine only after repeated failure.
4. Qualify several QPs sharing the engine, serialized as today. Parallel transactions need an operation id on the wire and are a later protocol change.
5. Then delete native, with RDMA READ and CM either dropped from the feature list or re-implemented on the descriptor path.

If instead general-purpose RDMA use stays a goal, keep both paths and do Phase 3 as written.

2. **RCU path table (O3).** Add `struct tbv_path_set { struct rcu_head rcu; u32 n; struct tbv_path *paths[]; }` per peer host, rebuilt under `state->lock` on rail ready, rail removal and host-id learning, and published with `rcu_assign_pointer`. `post_send` and the ACK sender read it under `rcu_read_lock` and take rail references with `refcount_inc_not_zero`. Rail teardown waits with `synchronize_rcu` before the final put. Gate: loopback test that adds and removes a link under traffic on the debug kernel; `lock_stat` shows `state->lock` off the data path.
3. **Receiver lookups (O5).** Hold an MR reference in `tbv_rx_reorder_msg` from first fragment to completion or drop; pass the header parsed in `tbv_path_rx_complete` into `tbv_ibdev_rx_native_frame`; change `tbv_qp_get_by_num` to `xa_load` under RCU with `refcount_inc_not_zero` and free QPs with `kfree_rcu`. Check MR deregistration: it must fail or wait while a reorder entry holds the MR, as it does today for in-flight sends. Gate: loopback with MR deregistration during a WRITE; qualify.
4. **Per-CPU counters (O4).** In the X-macro list mark the per-frame counters hot and back them with `alloc_percpu`; debugfs sums them. Gate: `perf c2c` on the receiver no longer lists the counter block; qualify.

### Phase 5: DMA-BUF transmit state machine

1. **Pure transition table (R3, R5).** Write `proto/dmabuf_tx_fsm.[ch]`: states `BUILD`, `ARM`, `POST`, `WAIT_DMA`, `WAIT_DONE`, `FINISH`, `ABORT`; events for READY, BUSY, RNR, DONE, credit, timeout, cancel, DMA complete, DMA error; output is the next state plus an action. Encode today's behavior exactly, including the cancel-drain rules of `5490050` and `d94fa1d`. Unit-test it in `tools/ci` with a table of sequences taken from the existing cancel and RX-state smokes and from `bench/results/2026-10-18-verbs-loss.md`.
2. **Drive `tbv_dmabuf_tx` from it.** Split the function body into one helper per action, called from a loop that feeds events to the table. `tbv_dmabuf_tx_direct` sets the initial state to `WAIT_DMA`; the two `goto` labels go. No timing change in this commit. Gate: all DMA-BUF smokes, then qualify including the kill and destroy cases.
3. **Retire extraction tests.** For each Python smoke whose logic now lives in `proto/`, replace it with a C test that links the real object, then delete the shim. Gate: `smoke_support.functions()` has no callers.
4. **Latency candidates (O6).** Only now, and each measured on its own: wake on BUSY-cleared in place of the 1 to 2 ms sleep; credits for small WRITEs. Keep a change only if the 4 KiB to 64 KiB latency sweep improves and Gufo throughput does not drop.

### What not to do

- Do not start Phase 3 or later before Phase 0 exists. The native path has no automated coverage today, and the two-host runs are too slow to catch a regression per commit.
- Do not combine a code move with a behavior change in one commit. The MR/CQ split was verifiable because it was a pure move.
- Do not parallelize the DMA-BUF engine as part of this work. Raw frames carry no operation id, so that is a wire protocol change with its own design.
